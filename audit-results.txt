## 1. Executive Summary

`redsocket_wgtcp` is the userspace WireGuard-over-TCP client library behind RostamVPN's WGTCP transport: boringtun for the Noise IK handshake and AEAD, smoltcp for an in-process TCP/IP stack, a loopback SOCKS5 front-end, and a TCP "record" carrier that frames WireGuard messages with an 8-byte header. Red Team Ltd reviewed every source file, ran the test suite (84 tests, all passing, offline) and a dependency audit, and re-verified the four WGTCP leads from the 2026-10-14 private-tree audit against this tree.

Overall posture. The cryptographic core is sound and the integration fails closed: the server's static key is pinned by Noise IK, keys come from the OS CSPRNG, a pre-shared key is supported, the record parser is bounds-checked against kernel golden vectors, there is no `unsafe` code, and when the carrier drops the library has no path by which application traffic can leave the host unencrypted. The dominant risk is not confidentiality but survivability under censorship: the carrier is a plaintext framing protocol with constant first bytes, fixed message sizes and fixed timers, so a national DPI operator can identify and block every WGTCP user from the first packet. Two integration issues compound this: the exported "connected" signal is raised on TCP accept before any handshake, and SOCKS5 domain targets are resolved by the host resolver outside the tunnel.

Findings: 10 — 1 High, 2 Medium, 4 Low, 3 Informational. RVPN-WG-010 (Informational) was remediated in the tree during the window and verified on re-check; 9 findings remain open.

Top three issues
1. RVPN-WG-001 (High) — the carrier is fingerprintable from its first 12 bytes; the header checksum is a public function of the length and provides no protection.
2. RVPN-WG-002 (Medium) — `carrier_is_up()` is true as soon as TCP connects, ~90 s of every retry cycle against a middlebox that accepts and discards, with no handshake ever completed.
3. RVPN-WG-003 (Medium) — hostnames given to the SOCKS5 front (the README's documented usage) are resolved in plaintext on the local network before entering the tunnel.

Headline recommendation. Do not enable WGTCP in a censored region until the record stream is wrapped in an obfuscation layer (or the header is replaced by a keyed, padded framing mirrored in the kernel module); gate "connected" on handshake completion; and resolve names inside the tunnel. The remaining items are hygiene that can ship with the next release.

### 2.1 Attack surface and assessment by area

Area 1 — Tunnel and leak integrity of the transport
- Egress paths that exist: (a) the carrier TCP socket to `endpoint` (carrier.rs:346-377), carrying WireGuard ciphertext in plaintext records; (b) host-resolver DNS for SOCKS5 ATYP 0x03 targets (socks5.rs:170); (c) host-resolver DNS for `endpoint` when it is a hostname (carrier.rs:348, :351). Nothing else: a failed tunnel connect returns `REP_HOST_UNREACHABLE` (socks5.rs:141-144); there is no direct-connect fallback anywhere.
- Guarantees: inner traffic only enters the tunnel via explicit SOCKS5 CONNECT (README.md:31-32); smoltcp emits only what the application wrote; the stack is single-family per config (lib.rs:37-44); a v6 target on a v4 tunnel fails at `connect` because the interface has no address of that family (smoltcp `ConnectError::Unaddressable`, vendor/smoltcp/src/socket/tcp.rs:1030-1031, surfaced as `REP_HOST_UNREACHABLE` via carrier.rs:218-223 and socks5.rs:141-144) — no path bypasses the tunnel.
- Carrier loss: `serve()` returns an error (carrier.rs:152-154, 182, 209); `CARRIER_UP` is cleared (:105); open streams are kept and their smoltcp sockets time out after 30 s (netstack.rs:182); new requests wait in a 128-slot channel (lib.rs:57); reconnect backs off 0.5 s doubling to 30 s (carrier.rs:31-32, 114-116) and forces a fresh initiation (wg.rs:94). boringtun clears an expired handshake on re-initiation (vendor/boringtun/src/noise/mod.rs:442-444), so a 90 s blackhole does not strand the client. Fail-closed.
- Keepalives: WireGuard persistent keepalive 25 s default (config.rs:19-21, config.example.toml:16); smoltcp per-socket keepalive 15 s (netstack.rs:183); boringtun KEEPALIVE_TIMEOUT 10 s. These are a fingerprint (area 4), not a leak.
- Checkpoint: findings RVPN-WG-002, -003; open: none.

Area 2 — Cryptography and key management
- Keys: `getrandom::fill` → `StaticSecret` (lib.rs:84-86); the CLI `genkey` uses OS-seeded `rand::rng()` with explicit clamping (main.rs:60-64). Peer pinning: `Tunn::new(static_private, peer_static_public, psk, keepalive, 0, None)` (wg.rs:66-75); Noise IK binds the responder's static key, so an impersonator needs the server's private key. PSK optional (config.rs:31-33), passed through (lib.rs:28, wg.rs:69). The carrier checksum (record.rs:26-34) is not a MAC and the README says so (README.md:61-62); integrity rests entirely on WireGuard's Poly1305 tag. boringtun 0.7.1 with no RustSec advisory. Replay: TAI64N check (vendor/boringtun/src/noise/handshake.rs:542-547) and the data-counter window in boringtun.
- Checkpoint: findings RVPN-WG-006 (storage/zeroization), -007 (keygen dependency); open: none.

Area 3 — Configuration and carrier
- Keys (config.rs:23-61, config.example.toml): `private_key`, `peer_public_key`, `preshared_key` (opt.), `endpoint` (`host:port`, validated only for a colon, config.rs:87-91), `address`, `gateway`, `prefix_len` (default 24), `socks_listen` (default 127.0.0.1:1080), `mtu` (default 1380, range-checked :114-121), `persistent_keepalive` (default 25). Supply: a TOML file for the CLI (`Config::load`, :68-74) or an in-memory `Config` for embedders (`run_tunnel`, lib.rs:22). There is no signature, versioning or provenance at this layer: the library pins whatever key it is given, so pinning is exactly as strong as the embedder's supply channel (the apps' unsigned-profile finding, out of scope).
- Downgrade: none available within the library — no transport negotiation, no UDP or plaintext mode (README.md:128-133), PSK cannot be stripped by the peer, `--socks` is the only CLI override (main.rs:36-38). A hostname `endpoint` adds a DNS dependency (RVPN-WG-003).
- Checkpoint: findings RVPN-WG-003 (endpoint resolution), -006, -009; open: D-1.

Area 4 — Network fingerprintability and active-probing resistance (central)
- Passive: every carrier connection begins with the same 12 bytes and continues with fixed sizes and timers; the full byte table and DPI narrative are in RVPN-WG-001.
- Active probing: the client exposes nothing to the network (SOCKS5 on loopback only). The in-tree server accepts any TCP connection, silently absorbs garbage through the resync parser, replies only to a valid initiation from a registered key, and never closes (src/server/run.rs:76-119, engine.rs:70-100) — WireGuard's silence property, but on TCP, where an open port that never speaks is itself a tell. The kernel-module server was not assessed.
- Checkpoint: finding RVPN-WG-001; open: D-2, D-3.

Area 5 — Data handling
- The library writes no files. stderr logging via env_logger with `RUST_LOG` override (main.rs:48, bin/server.rs:97). Private keys are never logged; public keys, the endpoint and (at debug) destinations are (RVPN-WG-005). `.gitignore:4-5` guards `/config.toml` and `/*.local.toml` only (RVPN-WG-006).
- Checkpoint: findings RVPN-WG-005, -006, -010.

Area 6 — Platform interaction
- Listener: SOCKS5 bound to `socks_listen`, no authentication, no bind-address policy (RVPN-WG-004). Socket-protection hook for VpnService.protect installed once and invoked before every carrier connect (carrier.rs:337-377; test :405-433). The `wgtcp-android` C ABI is out of scope and not assessed.
- Checkpoint: finding RVPN-WG-004.

Area 7 — Memory safety
- No `unsafe` in `src/`. Record parser: all indices guarded (record.rs:79-81, 97-104, 164-166, 206-209); 30 kernel golden vectors (:232-263). Buffers: 64 KiB carrier read buffer (carrier.rs:139), 65,567-byte boringtun scratch (wg.rs:14, :79), 256 KiB + 256 KiB per smoltcp socket (netstack.rs:17-18). Panics in non-test code: `expect`/`panic!` in `NetStack::new` (netstack.rs:138, 146, 152, 154) reachable only through an unvalidated in-memory `Config` (RVPN-WG-009); `getrandom` failure (lib.rs:85); server-side `Mutex::lock().unwrap()` (engine.rs:127, 172, 186; peers.rs) which turns a poisoned lock into a crash. No `[profile]` section, so the default `panic = "unwind"` applies to release.
- Checkpoint: findings RVPN-WG-008, -009.

Area 8 — Resilience
- Open-source circumvention tool: no anti-tamper expected. Reproducibility: vendored sources with lockfile checksums and `--remap-path-prefix` for `/Users` and `/home` (.cargo/config.toml:2, :11) — resolves the embedded-home-path finding of the private-tree audit. No `rust-toolchain.toml`; no `strip`/`lto` settings (defaults). Reconnect and expiry handling verified (area 1).
- Checkpoint: no findings; noted in RVPN-WG-007 (toolchain pin).

Area 9 — Dependencies
- `cargo audit --no-fetch`: 0 vulnerabilities, 1 warning (chacha20 0.10.1 yanked). Inventory in Appendix B. tokio is pulled with `features = ["full"]` (Cargo.toml:23), larger than the library needs.
- Checkpoint: finding RVPN-WG-007.

## 3. Severity Methodology

Impact tiers calibrated to the threat model: Critical — deanonymization of a user, or application traffic leaving the device unprotected while the embedder shows "connected" (outcomes A, B); High — the transport is identifiable and blockable at national scale, or a remote compromise of the client (C, D); Medium — misreported tunnel state, local abuse by a co-resident process, destination metadata exposure with preconditions; Low — hygiene and defence-in-depth. Likelihood: High — passive, no key, no preconditions; Medium — requires a network position, a local foothold or a specific configuration; Low — several preconditions.

| Impact \ Likelihood | High | Medium | Low |
|---|---|---|---|
| Critical | Critical | High | Medium |
| High | High | Medium | Low |
| Medium | Medium | Low | Low |
| Low | Low | Low / Info | Info |

A CVSS 3.1 vector is reported for every finding for comparability; fingerprintability and misreported state map poorly onto CVSS, so where the two disagree the matrix above governs and the finding says so. Status is CONFIRMED only where the behaviour was traced in code at the cited lines.

## 5. Detailed Findings

### RVPN-WG-001 — Carrier identifiable from the first packet: plaintext header, fixed sizes, fixed cadence
- Severity: High. Impact High (outcome C: a national DPI operator can identify and block every WGTCP user and enumerate the user base) × Likelihood High (passive, keyless, matches at TCP payload offset 0). CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:H (8.1).
- Status: CONFIRMED. Byte values were derived from the published formula and cross-checked against the kernel golden vectors in record.rs:232-263; on-wire sizes should be confirmed by the capture in Appendix C.
- Location: src/record.rs:26-34 (`header_checksum`), :37-56 (`encode`), :78-111 (`parse_header`); src/carrier.rs:134-137 (initiation is the first write on every connection); src/wg.rs:91-100; src/config.rs:19-21 and config.example.toml:16 (25 s keepalive); src/netstack.rs:14 (inner MTU 1380 → 1420-byte data records), :183 (15 s per-socket keepalive). Private-tree audit cited record.rs:66-85 and carrier.rs:150-154.
- Description: Each WireGuard message is prefixed by `len(be32) | type(u8)=0 | flags(u8) | checksum(be16)` where `checksum = rotl16((len>>16) ^ (len&0xFFFF) ^ (flags<<8|type), 5) ^ 0xA5A5` — a keyless, documented function of the length (README.md:61-66). The WireGuard message that follows is itself unencrypted in its type byte, three reserved zeros, indices, 64-bit counter and `mac2`. There is no TLS, padding, random prefix, length randomization or cover traffic, and sizes and timers are those of WireGuard plus a constant 8.
- Evidence:
  ```rust
  // record.rs:26-34
  fn header_checksum(total_len: u32, ty: u8, flags: u8) -> u16 {
      let mut ck: u16 = 0;
      ck ^= ((total_len >> 16) & 0xFFFF) as u16;
      ck ^= (total_len & 0xFFFF) as u16;
      ck ^= ((flags as u16) << 8) | (ty as u16);
      ck = ck.rotate_left(5);
      ck ^= 0xA5A5;
      ck
  }
  // carrier.rs:134-137
  let init = self.peer.initiate_handshake()?;
  let mut out = Vec::new();
  record::encode(&init, &mut out)?;
  wr.write_all(&out).await.context("write handshake")?;
  ```
  What a DPI operator sees on every connection (bytes 0–11 of the TCP payload; WireGuard sizes from vendor/boringtun/src/noise/mod.rs:82-85):

  | Record | Total bytes | Bytes 0–11 (hex) | Basis |
  |---|---|---|---|
  | Client's first bytes: handshake initiation (WG type 1, 148 B) | 156 | `00 00 00 9c 00 00 b6 25 01 00 00 00` | formula |
  | Server's first bytes: handshake response (WG type 2, 92 B) | 100 | `00 00 00 64 00 00 a9 25 02 00 00 00` | golden vector (100,0,0,43301) |
  | Cookie reply (WG type 3, 64 B) | 72 | `00 00 00 48 00 00 ac a5 03 00 00 00` | formula |
  | Idle keepalive, every 25 s (WG type 4, empty) | 40 | `00 00 00 28 00 00 a0 a5 04 00 00 00` | golden vector (40,0,0,41125) |
  | Full-size data record (inner 1380 B) | 1420 | `00 00 05 8c 00 00 14 25 04 00 00 00` | golden vector (1420,0,0,5157) |
  | Per-stream inner TCP keepalive, every 15 s (40-B IPv4 segment) | ~80 | `00 00 00 50 00 00 af a5 04 00 00 00` | derived; confirm by pcap |

  Further signature material: when the server is silent the 156-byte initiation is resent every REKEY_TIMEOUT = 5 s for REKEY_ATTEMPT_TIME = 90 s (vendor/boringtun/src/noise/timers.rs:21-22, :217-234); `mac2` is all-zero on first contact; data records carry a constant receiver index and a little-endian counter that starts at 0 and increments in clear; a rekey pair (156 + 100 bytes) recurs every 120 s of activity (timers.rs:19). The destination port is operator-chosen (51820 in config.example.toml:8), but using 443 does not help because the payload is not a TLS ClientHello.
- Impact: A single rule such as `tcp payload starts with 00 00 00 9c 00 00 b6 25 01 00 00 00` blocks the service with no false positives, and logging it enumerates users. The checksum gives no protection. This is the condition the private-tree audit rated HIGH and advised against enabling in a censored region; it holds unchanged in this tree.
- Reproduction: `nc -l 51820 | xxd | head -2` as the endpoint, then `redsocket-wgtcp run --config config.toml`; or `tcpdump -i any -X port 51820` on a real session; compare with the table. `cargo test record::` reproduces the checksum values.
- Recommendation: Short term, keep WGTCP disabled for censored paths. Medium term, wrap the record stream in an obfuscation layer with a plausible cover (TLS 1.3 with a uTLS browser fingerprint and random padding, or a keyed framing in the Shadowsocks-2022/obfs4 family with length and timing randomization). If the bespoke carrier must remain, replace the plaintext header: derive a per-connection key from the Noise static-static DH or the PSK, encrypt the length field (AEAD/SIV header as in Shadowsocks-2022), pad records to random lengths, jitter keepalives, and precede the initiation with a random-length preamble. Any header change must be mirrored in the kernel module (`kernel/socket.h`), which is why the wrapper is the pragmatic path.
- References: CWE-200, CWE-203, CWE-319; OWASP ASVS v4 V1.9.1, V9.1.1; WireGuard whitepaper §5.4 (silence, cookies); RFC 8446 §5.4 (record padding as prior art).

### RVPN-WG-002 — `carrier_is_up()` true on TCP accept, before any handshake
- Severity: Medium. Impact Medium (misreported state; outcome B's precondition, though no traffic escapes within this library) × Likelihood High (accept-then-discard is standard DPI behaviour; a revoked key produces the same silence). CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:L (6.5).
- Status: CONFIRMED.
- Location: src/carrier.rs:97-100 (flag set), :131-137 (handshake written later, never awaited), :105 (cleared on loss), :329-335 (`carrier_is_up`); src/wg.rs:151-153 (`time_since_last_handshake`, the correct signal). Private-tree audit cited carrier.rs:112 and wg.rs:181.
- Description: `Carrier::run` stores `CARRIER_UP = true` as soon as `connect_carrier()` returns a connected `TcpStream`; the initiation is written afterwards inside `serve()` and its completion is never consulted. With a middlebox that completes the TCP handshake and drops payload, or with an unregistered key (the server is silent by design, engine.rs:83-86), the flag stays true until boringtun gives up: after REKEY_ATTEMPT_TIME = 90 s `update_timers` returns `ConnectionExpired` (timers.rs:217-225) → carrier.rs:182 errors → flag false → backoff 0.5–30 s → reconnect → flag true again. The exported state reads "up" for about 90 s of every cycle, indefinitely, with no byte of application traffic ever carried.
- Evidence:
  ```rust
  // carrier.rs:97-105
  match self.connect_carrier().await {
      Ok(sock) => {
          log::info!("carrier established to {}", self.endpoint);
          CARRIER_UP.store(true, std::sync::atomic::Ordering::Relaxed);
          backoff = BACKOFF_MIN;
          if let Err(e) = self.serve(sock).await { log::warn!("carrier lost: {e:#}"); }
          CARRIER_UP.store(false, std::sync::atomic::Ordering::Relaxed);
  ```
- Impact: An embedder that gates its UI or its transport fallback on this flag (the private-tree audit traced exactly that use) shows "connected" with a dead tunnel and never falls through to a working transport. The user believes they are protected; inside this library their requests merely time out after 30 s (netstack.rs:182).
- Reproduction: `nc -l -p 51820 > /dev/null` as the endpoint; run the client; "carrier established" is logged at once and `carrier_is_up()` is true; after ~90 s "wireguard timers: connection expired" and a reconnect; repeat.
- Recommendation: Define readiness as "a handshake has completed on the current carrier": set the flag when `time_since_last_handshake()` first becomes `Some` (or shrinks) after a connect, clear it on `ConnectionExpired` and on carrier loss, and export a three-state `Connecting/Up/Down` plus `handshake_age()`. Add a test in which a listener that accepts and drops must never flip the flag. Sketch:
  ```rust
  // in serve(), after each decapsulate/update_timers:
  if !self.handshake_seen && self.peer.time_since_last_handshake().is_some() {
      self.handshake_seen = true; CARRIER_UP.store(true, Relaxed);

  ```
- References: CWE-754, CWE-392; ASVS v4 V1.11.1 (closest control; tracked primarily by CWE).

### RVPN-WG-003 — SOCKS5 domain targets and the endpoint name resolved by the host resolver outside the tunnel
- Severity: Medium. Impact High (destination metadata to the ISP; outcome A/B family) × Likelihood Medium (requires a client that sends names — which is the README's documented usage). CVSS:3.1/AV:A/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N (4.3). The private-tree audit rated the same behaviour LOW for the Android embedder, which sends IP literals; for the library and its CLI the documented path is the leaking one.
- Status: CONFIRMED (documented as a known limitation, README.md:222-227).
- Location: src/socks5.rs:121-127 and :165-181 (`tokio::net::lookup_host`, address choice :172-179); src/carrier.rs:347-349 (`TcpStream::connect(endpoint)`) and :351-354 (`lookup_host(endpoint)`, first address only); README.md:103 (`curl --socks5-hostname`).
- Description: Inner UDP is not implemented, so there is no in-tunnel resolver. Every ATYP 0x03 CONNECT triggers a plaintext A/AAAA query from the host resolver on the physical network before the connection enters the tunnel; a poisoned or NXDOMAIN answer becomes `REP_HOST_UNREACHABLE`. If `endpoint` is a hostname, it is likewise resolved by the host on every reconnect.
- Evidence:
  ```rust
  // socks5.rs:166-170
  async fn resolve(host: &str, port: u16) -> Option<IpAddr> {
      if let Ok(ip) = host.parse::<IpAddr>() { return Some(ip); }
      let addrs: Vec<SocketAddr> = tokio::net::lookup_host((host, port)).await.ok()?.collect();
  ```
- Impact: While the tunnel is up and reported as such, the ISP sees a time-stamped list of the hostnames the user visits and can block or redirect by DNS alone. The server's name, if a hostname is configured, is exposed on every reconnect.
- Reproduction: `tcpdump -ni any udp port 53` while running `curl --socks5-hostname 127.0.0.1:1080 https://example.com`; the query for `example.com` appears on the physical interface.
- Recommendation: (1) Resolve inside the tunnel: the TCP-only stack can already carry DNS-over-TCP (RFC 7766) or DoT to a resolver reached via smoltcp; inner UDP would allow plain DNS to the gateway. (2) Until then, fail loudly: add `resolve_domains = "refuse" | "system"` defaulting to `refuse`, replying 0x08 to ATYP 0x03 so leaks cannot be silent. (3) Require `endpoint` to be an IP literal, or resolve it through the embedder's protected path. (4) Correct README.md:228-229, which still says IPv6 targets are refused although socks5.rs:105-111 forwards them (test :282-313).
- References: CWE-200, CWE-319; ASVS v4 V9.1.1, V8.1.1; RFC 1928 §5.

### RVPN-WG-004 — Unauthenticated SOCKS5 front, no connection cap, 512 KiB eager buffers per stream
- Severity: Low. Impact Medium (local abuse, denial of service) × Likelihood Medium (needs a co-resident process; loopback is not UID-sandboxed on Android or desktops). CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:L (4.4); assessed Low per the matrix and consistent with the private-tree audit's "by design" note.
- Status: CONFIRMED.
- Location: src/socks5.rs:35-56 (accept loop, task per connection, no limit), :61-72 (any method list answered with NO AUTH); src/netstack.rs:17-18, :178-180 (256 KiB rx + 256 KiB tx allocated at connect); src/carrier.rs:226-227; src/config.rs:11-13 (default loopback); src/main.rs:36-38, :83-85 (`--socks` override, no loopback check).
- Description: The listener accepts every connection, selects method 0x00 even when the client did not offer it (RFC 1928 §3 requires 0xFF), and each CONNECT allocates half a megabyte of smoltcp buffers plus two 64-slot channels before the tunnel socket is even established. - Evidence:
  ```rust
  // socks5.rs:72            sock.write_all(&[SOCKS_VERSION, 0x00]).await?;
  // netstack.rs:178-179     let rx_buffer = tcp::SocketBuffer::new(vec![0u8; TCP_RX_BUF]);
  ```

### RVPN-WG-008 — Record parser re-copies and re-scans its whole buffer on every call (Informational)
- Severity: Informational. Impact Low (CPU amplification only; memory bounded) × Likelihood Low (requires the trusted server or a full on-path attacker, who could simply drop the connection). CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:L (3.7).
- Status: CONFIRMED.
- Location: src/record.rs:154-192 (`next_message`), :160 and :195-201 (`materialize` copies the whole `VecDeque` into `scratch` on every call), :204-210 (`find_resync_offset` tests every offset), :169/:176/:184 (`drain` from the front). - Description: A 64 KiB read holding minimum-size 40-byte records causes ~1,600 calls, each copying up to 64 KiB (tens of MB of memcpy per read); a peer that sends a valid header then trickles one byte at a time repeats a 64 KiB copy per byte. Not a vulnerability; it is on the hot path.
- Evidence:

- References: CWE-407; ASVS v4 n/a.

## 9. Appendix C — Recommended dynamic test plan

1. Wire fingerprint: Linux host, `tcpdump -i <uplink> -w wgtcp.pcap port 51820`; connect, idle 60 s, transfer 10 MB, idle 60 s. Expected: first 12 client bytes `00 00 00 9c 00 00 b6 25 01 00 00 00`, server `00 00 00 64 00 00 a9 25 02 00 00 00`, 40-byte records at 25 s, 1420-byte data records, ~80-byte records at 15 s per idle stream. Feed the pcap to Zeek/Suricata with a 12-byte content rule; expect 100% hit rate, 0 false positives on a control corpus.
2. Retry cadence: endpoint = `iptables -A INPUT -p tcp --dport 51820 -j DROP` after the TCP handshake (or `nc -l` discarding); expect 156-byte records every 5 s for 90 s, then reconnect; log `carrier_is_up()` via a 10-line embedder — expect true during the 90 s (RVPN-WG-002).
3. Active probing of the in-tree server: `nc` to the port, send 1 KiB random bytes, then a replayed captured initiation, then nothing for 10 min; expect no reply and no close in all three cases; compare with the kernel-module server.
4. DNS leak: `tcpdump -ni any udp port 53 or tcp port 53` while `curl --socks5-hostname 127.0.0.1:1080 https://example.com`; expect the query on the physical interface (RVPN-WG-003); repeat with `--socks5` (literal) and expect none.
5. Carrier loss and recovery: drop the path for 120 s mid-transfer; expect no packets to the destination outside the tunnel, stream EOF at ~30 s, reconnect with backoff ≤ 30 s and a fresh handshake; verify with the same pcap.
6. Local abuse: open 4,000 SOCKS5 CONNECTs from a second user account; record RSS and whether the tunnel process is killed (RVPN-WG-004); attempt `--socks 0.0.0.0:1080` and connect from another host.
7. Logging: `RUST_LOG=debug` session; grep stderr for destination IPs, hostnames and base64 keys (RVPN-WG-005).
8. Memory: `gcore` the client after `run`; grep for the base64 private key (RVPN-WG-006).
